# 组件抽离与封装规范

使用本文件判断是否需要从现有页面或组件中抽离组件、composable 或工具函数。抽离的目标是建立清晰职责边界，而不是单纯减少代码行数。

## 判断是否需要抽离

### 建议抽离的信号

出现以下一个或多个信号，并且抽离后边界更清晰时，考虑执行抽离：

- 一块 UI 具有独立、稳定的业务或展示语义，可以单独命名。
- 相同结构或行为已经在多处使用，或有明确的近期复用需求。
- 某部分拥有独立状态、交互、生命周期或需要单独清理的副作用。
- 父组件同时承担数据编排、业务流程和多个独立 UI 区域，存在多个变化原因。
- 独立测试该部分能显著降低测试复杂度或提高故障定位效率。
- 抽离后父组件能更清楚地表达页面结构和核心业务流程。

代码较长、模板嵌套较深、条件分支较多或参数传递较多只能作为观察信号，不能单独决定抽离。组件超过 200 行时应检查职责，但职责单一且边界清晰时可以保持现状。

### 不建议抽离的情况

- 只为了满足行数限制或让父文件看起来更短。
- 片段只使用一次、逻辑简单，抽离后没有独立语义。
- 新组件只是转发 DOM、样式或属性，没有封装行为和约束。
- 为尚未出现的复用场景提前设计通用组件。
- 抽离后需要传入大量零散 Props、转发大量事件，或依赖父组件内部实现。
- 父子组件必须频繁同步同一份状态，导致数据流比抽离前更复杂。

如果抽离增加了接口数量、跨文件跳转和理解成本，却没有改善职责、复用或测试，应保持内联或重新选择边界。

## 选择抽离目标

| 待抽离内容 | 目标 | 判断依据 |
| --- | --- | --- |
| 独立 UI、交互及其局部状态 | Vue 组件 | 可以通过清晰的输入、输出独立使用 |
| 可复用的响应式状态、生命周期或副作用管理 | composable | 不负责渲染，但依赖 Vue 响应式能力 |
| 无状态的数据转换、格式化或校验 | utils | 纯函数，不依赖组件实例和生命周期 |
| 页面数据编排和一次性简单结构 | 保留在页面 | 抽离不会形成更清晰的职责边界 |

不要为了复用逻辑创建无实际 UI 语义的组件，也不要把包含模板结构的能力隐藏在 composable 中。

## 设计组件边界

- 让页面或容器组件负责数据获取、流程编排和多个区域的组合。
- 让被抽离组件负责自身 UI、局部交互和可独立清理的副作用。
- 使用最小且稳定的 Props 输入和 Emits 输出，不让子组件直接修改父组件状态。
- 使用 Slots 暴露必要的结构扩展点，不把内部实现细节变成公共接口。
- 可复用展示组件避免直接依赖路由或全局 Store；由调用方传入所需数据和操作。
- 如果接口参数持续增加，先重新检查抽离边界，而不是继续增加透传属性。
- 抽离时保持原有行为、可访问性和样式作用域，不顺带进行无关功能重写。

组件接口的基础定义规则统一参见 `code-standards.md`。

## 选择存放位置

| 复用范围 | 目录 | 示例 |
| --- | --- | --- |
| 单个页面或业务模块内部 | `views/<feature>/components/` | 页面筛选区、页面私有弹窗 |
| 多个页面共享的业务语义 | `components/business/` | 用户卡片、订单状态面板 |
| 跨业务使用的基础能力 | `components/common/` | 基础容器、通用反馈组件 |
| 可复用响应式逻辑 | `composables/` | `useRequest.js`、`useSelection.js` |
| 纯数据处理 | `utils/` | 格式化、转换、校验函数 |

不要因为未来可能复用就直接放入全局公共目录。先使用最小复用范围，出现真实跨模块需求后再上移。

## 抽离流程

1. **识别职责**：描述待抽离内容负责什么、因为什么变化，并确认现有痛点。
2. **选择类型**：根据是否包含 UI、响应式能力或纯数据处理，选择组件、composable、utils 或保持内联。
3. **定义边界**：列出最小输入、输出、Slots、局部状态和需要清理的副作用。
4. **选择位置**：按照实际复用范围放入页面私有、业务公共或基础公共目录。
5. **迁移实现**：保持功能和数据流不变，先完成机械迁移，再处理确有必要的内部整理。
6. **验证结果**：运行相关测试和交互检查，确认父组件更易理解且新接口没有增加耦合。

## 检查清单

- [ ] 抽离对象具有可描述的独立职责或真实复用需求
- [ ] 抽离依据不只是文件行数或模板长度
- [ ] 已选择组件、composable、utils 或保持内联中的正确目标
- [ ] 输入、输出和 Slots 数量合理，没有暴露父组件内部细节
- [ ] 新位置与实际复用范围一致，没有过早提升为全局组件
- [ ] 状态归属和单向数据流清晰，没有复制同一份状态
- [ ] 事件监听、计时器和其他副作用可以独立清理
- [ ] 抽离前后的行为、样式、可访问性和测试结果一致
