# 无设计稿的界面质量检查

本文档详细介绍在没有UI设计稿的情况下，如何对功能页面进行规范走查和质量检查，确保界面遵守项目类型特定的规范要求。

---

## 1. 任务介绍

### 1.1 任务目标

你的任务是对当前的功能页面进行走查，需要确保界面遵守项目类型特定的规范要求，保证功能的正确性和界面的规范性。

### 1.2 适用场景

- 前端功能模块开发完成后，没有UI设计稿但需要进行质量检查
- 已有功能页面需要验证是否符合项目规范
- 页面样式调整后需要验证功能和规范性
- 需要确保界面遵守大屏项目或PC端项目规范

---

## 2. 需求判断

### 2.1 项目类型判断

结合已发生的对话内容和用户补充的信息，推断当前项目属于大屏项目还是PC端普通网页项目。

**重要：** 如果不确定项目类型，**必须**让用户补充。此步骤不可跳过。

#### 2.1.1 判断依据

**关键词识别**：
- **大屏项目关键词**：大屏、可视化大屏、数据可视化、指挥中心、展厅、数字孪生
- **PC端项目关键词**：管理后台、admin、业务系统、企业应用、响应式、计算运维管理

**项目特征分析**：
- **尺寸特征**：固定尺寸（4352x1536）→ 大屏项目；响应式布局 → PC端项目
- **组件库特征**：使用 origami-vue → PC端项目；不使用 origami-vue → 可能是大屏项目
- **技术栈特征**：使用 ECharts、@tslfe/dt-engine → 可能是大屏项目

#### 2.1.2 判断流程

```
获取对话上下文信息
  ↓
分析关键词和项目特征
  ↓
项目类型确定？
  ├─ 是 → 进入对应规范检查
  └─ 否 → 向用户询问项目类型（不可跳过）
```

#### 2.1.3 项目类型对照表

| 项目类型 | 必激活特定 skill | 关键词特征 | 组件库 |
|----------|----------------|-----------|--------|
| **大屏项目** | tsl-big-screen-best-practices | 大屏、可视化、数字孪生 | 不使用 origami-vue |
| **PC端项目** | tsl-admin-best-practices | 管理后台、admin、业务系统、响应式 | origami-vue（推荐） |

### 2.2 信息收集

如果项目类型判断不明确，需要向用户询问以下信息：

- 项目的主要用途是什么？（管理后台、数据可视化大屏、其他）
- 项目的目标屏幕尺寸是什么？
- 项目使用的主要组件库是什么？
- 项目是否有特定的技术栈要求？

## 4. UI走查

### 4.1 启动开发调试服务

在进行UI还原度走查前，需要先在本地启动开发调试服务：

```bash
# 根据项目配置选择启动命令
npm run dev
# 或
npm run serve
```

等待服务启动完成，记录本地访问地址（如 `http://localhost:3000`）。

### 4.2 使用 Chrome DevTools MCP 工具检查

使用 Chrome DevTools MCP 工具访问当前功能模块的路径，进行以下检查：

#### 4.2.1 检查控制台错误

使用 `list_console_messages` 工具检测控制台是否有错误：

```javascript
// 过滤错误和警告类型
types: ["error", "warn"]
```

**检查要点**：
- 是否有 JavaScript 错误
- 是否有 API 请求错误
- 是否有资源加载错误
- 是否有样式警告

#### 4.2.2 验证功能模块正常性

使用以下工具验证功能：

| 工具 | 用途 | 验证内容 |
|------|------|---------|
| `take_snapshot` | 获取页面元素快照 | 验证页面结构、元素是否存在(注意：截图前需要等页面完全加载完，且如果是大屏项目时必须根据页面的实际尺寸对页面进行缩放) |
| `click` | 点击按钮 | 验证交互功能、按钮响应 |
| `hover` | 悬停验证 | 验证样式变化、提示信息 |
| `type_text` | 输入文本 | 验证表单功能、输入验证 |
| `press_key` | 按键操作 | 验证快捷键、键盘导航 |

**验证步骤**：
1. 使用 `take_snapshot` 获取页面结构(注意：截图前需要等页面完全加载完，且如果是大屏项目时必须根据页面的实际尺寸对页面进行缩放)
2. 定位关键按钮和交互元素
3. 使用 `click` 验证按钮功能
4. 使用 `hover` 验证样式变化
5. 使用 `type_text` 验证表单输入

#### 4.2.3 检查页面数据渲染

通过 `take_snapshot` 获取页面内容，确认数据是否正常渲染：

**检查要点**：
- 数据是否正常显示
- 空状态是否正确处理
- 加载状态是否正确显示
- 错误状态是否正确提示
- 注意：截图前需要等页面完全加载完，且如果是大屏项目时必须根据页面的实际尺寸对页面进行缩放

### 4.3 遵守项目类型特定规范

根据项目类型判断结果，检查UI界面是否遵守对应的规范。

#### 4.3.1 大屏项目规范（tsl-big-screen-best-practices）

如果当前项目是大屏项目，检查UI界面是否遵守 `tsl-big-screen-best-practices` skill 规范：

**核心规范要点**：

| 规范项 | 检查内容 |
|--------|---------|
| **尺寸适配** | 基准尺寸为 1920x1080，使用缩放适配方案 |
| **图表规范** | ECharts 图表配置是否符合大屏规范 |
| **样式系统** | 使用 Less 样式系统，样式组织是否合理 |
| **布局结构** | 卡片、面板、装饰元素是否遵循大屏设计 |
| **动画效果** | 页面切换动画、数据更新动画是否流畅 |
| **组件库** | 不使用 origami-vue，使用专门的图表库 |
| **性能优化** | 图表渲染性能、数据更新频率是否合理 |

**检查流程**：
```
1. 激活 tsl-big-screen-best-practices skill
   ↓
2. 阅读规范要点
   ↓
3. 使用 Chrome DevTools MCP 检查界面
   ↓
4. 对照规范逐项检查
   ↓
5. 发现不符合规范的地方 → 修改 → 重新检查
   ↓
6. 完全遵守规范 → 完成
```

#### 4.3.2 PC端项目规范（tsl-admin-best-practices）

如果当前项目是PC端普通网页项目，检查UI界面是否遵守 `tsl-admin-best-practices` skill 规范：

**核心规范要点**：

| 规范项 | 检查内容 |
|--------|---------|
| **组件库使用** | origami-vue 组件是否正确使用（OriButton、OriTable、OriForm 等） |
| **基础字号** | 基础字号为 14px，是否符合规范 |
| **主色调** | 紫蓝主色调，颜色使用是否符合设计规范 |
| **布局模式** | 管理后台布局模式，导航、侧边栏、内容区是否合理 |
| **表格规范** | OriTable 使用是否规范，列配置、分页、筛选是否正确 |
| **表单规范** | OriForm 使用是否规范，验证、提交、重置是否正确 |
| **详情页规范** | 详情页布局、信息展示是否规范 |

**检查流程**：
```
1. 激活 tsl-admin-best-practices skill 和 origami-vue skill
   ↓
2. 阅读规范要点
   ↓
3. 使用 Chrome DevTools MCP 检查界面
   ↓
4. 对照规范逐项检查
   ↓
5. 发现不符合规范的地方 → 修改 → 重新检查
   ↓
6. 完全遵守规范 → 完成
```

### 4.4 样式修改与重新检测

**重要原则**：每一次进行了界面样式修改，都需要重新使用 Chrome DevTools MCP 工具，访问当前功能模块的路径，进行完整检查。

#### 4.4.1 迭代验证循环

```
发现样式问题
  ↓
修改样式代码
  ↓
保存文件（热更新）
  ↓
使用 Chrome DevTools MCP 重新访问
  ↓
检查控制台错误
  ↓
验证功能是否正常
  ↓
检查是否遵守规范
  ↓
符合规范？
  ├─ 是 → 继续检查其他项
  └─ 否 → 重新修改样式 → 循环
```

#### 4.4.2 重新检测要点

每次修改后必须重新检测：

1. **控制台检查**：确认没有引入新的错误
2. **功能验证**：确认修改没有破坏现有功能
3. **规范检查**：确认修改符合项目规范
4. **视觉效果**：确认样式效果符合预期

**重要提示**：
- 不要跳过检测环节
- 不要一次性修改多处样式后再检测
- 确保每次修改都经过验证

### 4.5 完成后关闭开发服务

所有检查项都完成且满足要求后，关闭本地的开发调试服务：

```bash

```

## 6. 常见问题处理

### 6.1 项目类型判断困难

**问题描述**：无法确定项目属于大屏项目还是PC端项目。

**解决方案**：
1. 检查项目的技术栈配置（package.json）
2. 查看项目的路由配置和页面结构
3. 检查是否有尺寸适配方案
4. 直接询问用户项目类型

### 6.2 控制台有错误但无法定位

**问题描述**：控制台有错误日志，但无法准确定位问题代码。

**解决方案**：
1. 使用 Chrome DevTools 的 Sources 面板查看错误堆栈
2. 检查网络请求是否有错误
3. 使用 `get_console_message` 获取详细错误信息
4. 参考 bug-fix.md 进行系统化排查

### 6.3 样式修改后引入新问题

**问题描述**：修改样式后，控制台出现新的错误或功能异常。

**解决方案**：
1. 立即停止修改，回滚到修改前状态
2. 使用 Chrome DevTools MCP 重新检测
3. 分析样式修改的影响范围
4. 采用最小化修改原则，逐个属性调整

### 6.4 规范检查无法通过

**问题描述**：界面始终无法符合项目规范要求。

**解决方案**：
1. 重新激活对应的 skill，仔细阅读规范要点
2. 使用 Chrome DevTools 检查元素的样式属性
3. 与规范要求进行逐项对比
4. 必要时请求有经验的开发者协助

### 6.5 MCP 工具调用失败

**问题描述**：Chrome DevTools MCP 工具无法正常访问页面或获取信息。

**解决方案**：
1. 确认开发服务是否正常运行
2. 检查浏览器是否已经打开页面
3. 确认页面 URL 是否正确
4. 查看 MCP 服务日志排查问题
5. 参考 MCP 工具文档确认参数格式
